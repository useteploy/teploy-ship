# Deliberate termination (task 4), A/B on SWE-bench Lite — 2026-08-18

**Result: no measurable effect on score.** The mechanism works exactly as
designed; it does not convert into resolved instances.

| | resolved | |
|---|---|---|
| settle **off** (the 35/50 baseline) | 34/49 | 69.4% |
| settle **on** (`SHIP_FINISH_WHEN_SETTLED=1`) | **36/49** | 73.5% |

Nominally +2. Eight instances flipped — 5 gained, 3 lost — and **McNemar on
those discordant pairs gives p = 0.73**. That is indistinguishable from noise.
Do not report this as an improvement.

```
gained: matplotlib-25332  sphinx-7738  sympy-16281  sympy-17655  sympy-18087
lost  : pytest-7220  sphinx-8627  sympy-20049
```

Controlled: same seeded instance set, same model (glm-5.3), same thinking
budget (32768), same step cap (40), same host. One variable.

n = 49 rather than 50 because `sympy-18621` was skipped — see below.

## What DID change: how runs end

Thrash-aborts collapsed and the settled exit fired in their place. On the
partial data (34 instances) aborts went 10 -> 1, with 8 settled exits, and
empty patches went down rather than up.

So the nudge does what it was built to do. The score simply does not move,
which means **the 30% thrash-abort rate was not costing us resolved
instances** — those runs were already holding whatever patch they were going
to produce, and the abort was a labelling problem rather than a lost fix.

That contradicts the framing this task carried into the work, where
termination was called "the largest measured failure mode and the best
remaining lever". It was the largest *failure-mode* by count. It was not a
lever on score. Treat a process metric as a hypothesis about the score, never
as a proxy for it.

## Keep it or drop it?

**Keep, default off.** It costs nothing, it makes run endings honest
(`settled` rather than a spurious `error`), and an error status that does not
mean an error is its own small lie in the logs. But it is not a quality
improvement and must not be sold as one.

The remaining question it raises is narrower than the one it answered: the
nudge fires on ANY run spinning over a dirty tree, including runs that would
have finished by themselves. Two of the three losses look like exactly that.
Gating it on "a finish has already been held" — the actual measured pathology
— is a cheap follow-up, and would be a genuinely different experiment.

## Infrastructure notes that earned their keep

**The resilience work paid off on its first real run.** The same Tailscale
MagicDNS failure that destroyed the previous sweep (killing it at instance 46
and losing 45 completed instances) hit again, on `sympy-18621`. This time the
harness retried the pull, gave up on that one instance, recorded it as skipped,
completed the other 49, and exited 4 to flag itself PARTIAL. Every prediction
survived.

**Two instances failed scoring with image-pull 404s** — infra, not model.
Re-scoring just those two recovered `matplotlib-23913` as RESOLVED. Without
that check the result would have read 35 instead of 36, understating the run,
which is the identical trap that produced a bogus 17/50 earlier in the week.

**Always check `error_instances` before believing a score.** Errors clustered
by repo, or any error at all on a previously-clean instance, mean image-pull
failure rather than model failure.
