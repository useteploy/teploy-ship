PROOF A — Chromium through teploy-sandbox's per-run AUTHENTICATED egress proxy
2026-10-14 · branch proof/egress-browser-proxy-2026-10-14 (worktree, docs-only) · receipt

==============================================================================
0. QUESTION
==============================================================================
Can Chromium reach the internet inside an allowlist-tier sandbox run, given
that the per-run egress proxy requires Proxy-Authorization and the credential
only rides the HTTP(S)_PROXY URL userinfo? Hypothesis under test (from
docs/PERCEPTION_INPUT_S12_S13_2026-10-14.md §2, "unverified live"): a naive
Chromium launch that only inherits the proxy env vars fails (407 expected);
the fix is Playwright's explicit proxy:{server,username,password}.

VERDICT UP FRONT: hypothesis CONFIRMED live, with one correction — Chromium
on Linux headless DOES read the env proxy vars (lowercase), but strips the
URL userinfo, so every tunnel dies at the daemon's 407. Playwright's
explicit proxy option works end-to-end (200, real DOM, page title).

1. CODE-LEVEL ANALYSIS (read before any live run; teploy-sandbox @ main)
==============================================================================

Proxy URL shape — internal/egress/pool.go:102-148 (OpenFor):
  - per-run listener on the egress bridge gateway, kernel-picked port
  - credential = 32 random bytes, hex-encoded (64 chars), pool.go:102-107
  - URL built at pool.go:147:
        u := &url.URL{Scheme: "http", Host: listener.Addr().String(),
                      User: url.UserPassword("run", credential)}
    => EXACT SHAPE:  scheme http, host 172.31.99.1:<ephemeral-port>, userinfo
       "run" ":" <64-hex-chars>  (credential travels as URL userinfo)
    (The SHARED deployment-wide proxy, http://172.31.99.1:7443, carries NO
     credential — Credential=="" skips the auth gate entirely, pool.go:271.)

Auth check — internal/egress/proxy.go:271-278 (ServeHTTP):
  - expected = "Basic " + base64("run:" + credential), constant-time compare
  - ANY missing/wrong Proxy-Authorization on ANY method (CONNECT included):
    407 + `Proxy-Authenticate: Basic realm="sandbox"` + body "proxy
    credential required". The auth gate runs BEFORE the allowlist check,
    so an unauthenticated request never reveals whether its host is allowed.

Allowlist gate — internal/egress/proxy.go:178-210 (Permits), 289, 316:
  - host[:port] entries; bare host admits ONLY ports 80/443; denial = 403
    "egress denied by the sandbox allowlist: <host>" + remedy text.

Env injection — internal/run/runtime.go:223-235 (createArgs):
  - allowlist runs join network teploy-sbx-egress-v2 (internal bridge
    teploy-sbx1, subnet 172.31.99.0/24, gateway 172.31.99.1, ICC off,
    IPv6 disabled; runtime.go:74-83, 226), and get, with the URL INCLUDING
    userinfo: HTTP_PROXY, HTTPS_PROXY, http_proxy, https_proxy
    + NO_PROXY/no_proxy=localhost,127.0.0.1.
  - i.e. the daemon already does the best env-var job possible: all four
    spellings carry run:<credential>@. If Chromium ignores URL userinfo,
    no env arrangement can fix it — it must be a launch option.

Container hardening relevant to a browser: --init, --shm-size 512m
(main.go:111 SBX_SHM_MB default 512 — "Chromium needs 512 MB or more"),
--cap-drop NET_RAW/MKNOD/AUDIT_WRITE, no-new-privileges, default limits
1 CPU / 1024 MB / 256 pids (README; manager CreateSpec defaults).

Daemon startup — main.go:124-158:
  - On a Mac dev box (docker-in-VM): EgressGateway() returns an IP that is
    NOT a host interface; the daemon logs "egress proxy disabled" and runs
    allowlist-tier runs FULLY SEALED (main.go:136-138 comment says exactly
    this). => A live proof cannot run the daemon on the macOS host against
    colima; the daemon must run inside the Linux VM (or a real Linux box).
    Honored here: daemon ran inside the colima VM as root (iptables for the
    TEPLOY-SBX INPUT chain + /var/run flock + gateway bind).

Expected outcomes from code alone:
  a. curl WITH env userinfo → Proxy-Authorization on CONNECT → 200.
  b. curl to non-allowlisted host → 403 + remedy.
  c. chromium env-only → either ignores env (no route/DNS on internal
     bridge) or applies env minus userinfo → 407 at CONNECT → net error.
  d. Playwright proxy:{server,username,password} → CDP auth handling → 200.

4. LIVE RESULTS — Chromium WITHOUT explicit proxy credentials (the failure)
==============================================================================
Chromium 155.0.8059.39 (Debian trixie apt), headless=new, in-run.

C1 env-only launch (exactly what a naive driver would inherit):
  $ chromium --headless=new --no-sandbox --disable-gpu --dump-dom \
        --virtual-time-budget=15000 https://example.com/
  exit=0, DOM output = 0 bytes. Stderr: only container-noise dbus errors.
  SILENT FAILURE — exit code 0 with empty output.

C1 netlog (--log-net-log), the mechanism, verbatim:
  PROXY_CONFIG_CHANGED {"new_config":{"bypass_list":["*localhost","127.0.0.1"],
    "proxy_per_scheme":{"http":["[172.31.99.1:39525]"],
                        "https":["[172.31.99.1:39525]"]}}}
    => Chromium DID read the lowercase env vars and adopted the proxy —
       but the bracket form carries NO identity: the URL userinfo was
       STRIPPED. (no_proxy became the bypass list, as expected.)
  HTTP_TRANSACTION_SEND_REQUEST_HEADERS
    {"line":"CONNECT example.com:443 HTTP/1.1","headers":["Host: example.com:443",
     "Proxy-Connection: keep-alive","User-Agent: …HeadlessChrome/155…"]}
    => no Proxy-Authorization header on the main-frame CONNECT.
  HTTP_TRANSACTION_READ_RESPONSE_HEADERS
    ["HTTP/1.1 407 Proxy Authentication Required",
     "Proxy-Authenticate: Basic realm=\"sandbox\"", …]
    => the daemon's exact 407 (proxy.go:274-275), logged by Chromium itself.
  HTTP_PROXY_CONNECT_JOB_CONNECT {"net_error": -3}        (ERR_ABORTED)
  REQUEST_ALIVE               {"net_error": -111}         (ERR_TUNNEL_CONNECTION_FAILED)

C2 explicit --proxy-server=http://172.31.99.1:39525 (no credentials):
  identical outcome: PROXY_CONFIG_CHANGED single_proxy [172.31.99.1:39525],
  CONNECT without auth → 407 → net_error -111, --dump-dom 0 bytes, exit 0.

C-NAIVE the same failure through Playwright WITHOUT proxy option
  (node -e, chromium.launch({executablePath:'/usr/bin/chromium'}) — env
  inherited, which is precisely the "just launch it" driver):
    page.goto: net::ERR_INVALID_AUTH_CREDENTIALS at https://example.com/
    Call log: navigating to "https://example.com/", waiting until "load"
  => a naive Playwright driver does not hang or time out; it fails fast
     with ERR_INVALID_AUTH_CREDENTIALS (Chromium saw the 407 challenge it
     cannot answer). Catchable, testable, honest.

Also observed in C1/C2 netlogs (operationally relevant):
  Chromium background services hit the proxy constantly even before the
  navigation: clients2.google.com/time/1 (absolute-form GET through the
  proxy), CONNECT redirector.gvt1.com:443 (spellcheck dict),
  CONNECT update.googleapis.com:443, accounts.google.com. They all met the
  same 407 here; WITH valid credentials they would meet 403 (not on the
  default allowlist) — benign for navigation, but the driver should pass
  --disable-background-networking to keep the proxy log legible.
  DNS probes: SOCKET_CONNECT [2001:4860:4860::8888]:443 net_error -108
  (ERR_ADDRESS_UNREACHABLE) — Chromium's DoH fallback cannot escape the
  internal bridge either.

wss (observational, as planned): a page-level WebSocket('wss://example.com/')
  failed FAST with onerror (not timeout), and the daemon logged NO "egress
  denied" for it — the CONNECT tunnel was established and example.com (not a
  ws origin) refused the upgrade. Transport-level evidence that wss rides
  the authenticated CONNECT tunnel like any other TCP. A live websocket
  ECHO origin was not tested (none is allowlisted; deliberately not added).

DNS (observational):
  $ getent hosts example.com   → exit 2 (no result)
  $ curl --noproxy '*' https://example.com/ → Could not resolve host
  => container-side external DNS is dead on the internal bridge (docker's
     embedded resolver cannot forward); hostnames of proxied traffic are
     resolved PROXY-side, inside the daemon. A non-proxy-aware client fails
     at resolution before it ever touches the network — defense in depth
     on top of the no-route bridge.

7. CONCLUSIONS
==============================================================================
MEASURED (live, this proof, local VM):
 1. The per-run proxy URL is exactly: host 172.31.99.1:<port>, userinfo
    "run" ":" <64-hex credential> (credential in the userinfo position)
    (code pool.go:147; observed in-run env; port 39525 for run
    01M4YTVBXA3EV2SYEWRTG3A2T8).
 2. Proxy auth is enforced on both plain absolute-form requests and CONNECT:
    no/wrong credentials → 407 + Proxy-Authenticate: Basic realm="sandbox"
    (code proxy.go:271-278; observed by curl A2 and in Chromium's netlog).
 3. The allowlist fence works: non-allowlisted host → 403 + remedy naming
    the exact egressAllow entry (observed for www.wikipedia.org:443).
 4. curl (proxy-aware) reaches the allowlisted host THROUGH the env URL's
    embedded credentials: 200, real body (A).
 5. Chromium headless=new on Linux READS the lowercase proxy env vars
    (http_proxy/https_proxy; no_proxy → bypass list) — the plan's aside
    that it "does not read http_proxy env at all" is NOT true of this
    build — but it STRIPS the userinfo, so it uses the proxy UNAUTHENTICATED:
    main-frame CONNECT example.com:443 went out with no Proxy-Authorization,
    was answered 407, and the job died ERR_TUNNEL_CONNECTION_FAILED (-111)
    with ERR_ABORTED (-3) at the connect job.
 6. --dump-dom makes that failure SILENT: exit code 0, zero bytes of output.
 7. Naive Playwright launch (no proxy option) fails fast and catchably:
    page.goto: net::ERR_INVALID_AUTH_CREDENTIALS.
 8. Playwright chromium.launch with EXPLICIT proxy:{server,username,password}
    parsed from the injected env URL reaches the allowlisted site: goto 200,
    title "Example Domain", real DOM — under default run limits
    (1 CPU / 1 GB / 256 pids / 512M shm).
 9. Container-side external DNS resolution fails on the internal bridge;
    proxied hostnames resolve proxy-side. Direct (non-proxy) sockets have
    no route regardless.
10. wss: a page WebSocket through the tunnel reached the origin (fast
    onerror, no daemon-side denial). Transport-level only.

INFERRED (reasoned, not fully measured):
 - Chromium background services with VALID credentials would draw 403s
   (they 407'd before the allowlist check here). Adding
   --disable-background-networking to the driver is hygiene, not security.
 - A live websocket echo origin would succeed through the tunnel (CONNECT
   is a bidirectional raw-TCP tunnel — io.Copy both ways, proxy.go:363-364 —
   and TLS-through-tunnel is proven by every https request above); not
   measured against a real ws server.
 - The same behavior should hold for chromium-on-gVisor (runsc) since the
   proxy interaction is userspace; not measured.

WHAT THE SHIP BROWSER DRIVER MUST DO (the fix, as run in §5):
  // allowlist tier: HTTPS_PROXY carries run:<credential>@ — decompose it,
  // never pass it through as a URL with userinfo.
  const raw = process.env.HTTPS_PROXY ?? process.env.https_proxy ?? "";
  let proxy;
  if (raw) {
    const u = new URL(raw);                    // raw: host 172.31.99.1, userinfo run:<cred>
    proxy = {
      server: `${u.protocol}//${u.host}`,      // NO userinfo
      username: decodeURIComponent(u.username),// "run"
      password: decodeURIComponent(u.password),// per-run credential
    };
  }
  const browser = await chromium.launch({
    executablePath: process.env.CHROMIUM_BIN ?? "/usr/bin/chromium",
    args: ["--no-sandbox", "--disable-gpu", "--disable-background-networking"],
    proxy,                                     // undefined on the open tier —
  });                                          // no proxy env is injected there
  Rules that follow: treat goto() exceptions as the error surface (never a
  dump-dom exit code); keep NO_PROXY covering localhost for in-run preview
  servers (already injected by the daemon); on the open tier pass NO proxy
  option at all (runtime.go:236-243 injects none, and a stale one would
  re-impose the fence the caller opted out of).

SURPRISES worth carrying into S12:
 - env-var proxying is HALF-honored (proxy yes, credentials no) — worse than
   plain "ignored" because the traffic still concentrates on the proxy and
   fails closed, which is the correct security posture but a confusing UX.
 - exit 0 on failed --dump-dom: any future driver built on raw chromium
   flags must not trust exit codes.
 - ERR_INVALID_AUTH_CREDENTIALS (Playwright/CDP path) vs
   ERR_TUNNEL_CONNECTION_FAILED (raw dump-dom path) — two different net
   errors for the same underlying 407.
