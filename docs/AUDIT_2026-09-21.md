# Release programme audit — 2026-09-21

Incremental local code/dependency review, not an external ChatGPT audit or a
completed repository security audit. The dependency correction below does not
close the broader request/approval, project access, preview and recovery review.

## F01 — Tested and deployed dependency trees diverged

Confirmed. Docker installed `deploy/package.web.json`, whose Neutron CLI/core
pins were 0.1.4/0.1.8 while local suites used 0.2.3/0.2.2. Deployment also omitted
all pnpm security overrides. Vite/preset and pg pins differed. Testing local
routes therefore did not prove the behavior or patched dependencies deployed.
Both Docker installs resolved transitives without lockfiles; exact direct pins
did not make repeated builds reproducible.

Fix: align production direct pins with installed tested versions, carry web
security overrides into npm, commit separate production npm lockfiles and use
`npm ci` for both image installs. Seam tests compare installed versions,
overrides, lockfile roots, registry integrity and Docker's frozen installs.
CI installs both local dependency sets before those tests. Audit CI now checks
web dependencies and both production lockfiles, including the SSR toolchain.
`node scripts/audit-deployment.mjs` audits the exact committed production trees.
The remaining container/CLI inventory review is open.

## F03 — Project identity loses the forge origin (migration implemented; see continuation)

Confirmed with `FileProjectStore`; Nucleus uses the same `repoSlug` lookup.
Registering `https://github.com/team/app` and then looking up
`https://forge.example/team/app` returns the GitHub project's configuration.
This can apply the wrong project defaults, budget, automation or service mapping
when installations allow same-named repositories on multiple forges. This pass
has not established credential leakage or an allowlist bypass.

Reproduction: create a temporary FileProjectStore, set
`{ repo: "team/app", url: "https://github.com/team/app", autoMerge: false,
autoDeploy: false, dailyBudgetUSD: 1 }`, then call
`forRepo("https://forge.example/team/app")`. It returns the registered GitHub row.
`src/projects.ts` stores and retrieves projects by owner/name without origin.

Owner: Ship project identity, S03/S05. This needs an origin-qualified canonical
identity with backward-compatible legacy aliases, not a display-only fix.
Review evidence, policy, schedules, intake, memory and deployment references
before migration. Define explicit SSH/HTTPS clone aliases rather than guessing
that matching host/path implies the same repository. Preserve legacy stored
runs and refuse ambiguous legacy resolution. Acceptance: same owner/name on
GitHub and Forgejo remain independent through setup, enqueue, budgets,
automation and service attribution; old unambiguous projects still resolve.

Containment: project URL lookups now reject a conflicting origin, scheme or
port. Writes cannot replace or clear an established clone identity; removals
validate the reference. File writes serialize the identity check with the write;
Nucleus uses a conditional document comparison so a concurrent edit cannot be
overwritten after validation. Worker intake validates cached project references
before applying automation policy, and budget lookup no longer hides errors.
The isolated restored Nucleus v1.1.1 engine passed concurrent registration,
wrong-origin lookup/update/removal and an injected read/write race using
`scripts/check-project-identity.mjs`.

Compatibility: bare slugs remain explicit administrative references. A legacy
record without a clone URL must be bound explicitly in Projects before it can
supply settings to a URL-based request. History remains readable with a repair
notice; stored run inputs and workflow steps are unchanged. No legacy records
were automatically rebound. SSH/HTTPS aliases are not inferred.

The initial containment above did not implement multiple same-slug projects
or migrate related scopes. The full-origin continuation below supersedes that
limit. Project access control remains separate release-programme work.

## F04 — Framework upgrade changed the container bind default

The first deployment of F01 failed its external health check: the newer Neutron
preview server listens on 127.0.0.1 by default. Its startup log looked healthy,
but Docker's published port could not reach it. The failed replacement was
removed by deployment tooling; the prior web container was explicitly restarted
and verified responding before retrying.

Fix: configure the host through `SHIP_WEB_HOST`, retain loopback for local
preview and explicitly set `0.0.0.0` in the deployment image. The corrected
config was exercised in an isolated container through a published loopback host
port, without production credentials/data. CI now loads and starts the actual
built image, checking login and authenticated setup through its published port.
`bash scripts/smoke-image.sh IMAGE` reproduces that check. This catches a class
of deployment regressions that source tests and browser builds cannot detect.

## F05 — Concurrent file-store decision claims all succeeded

Reproduced: eight simultaneous claims for one parked approval returned eight
winners. Single-process file mode has concurrent HTTP handlers; plain
read-check-write does not serialize them. RunMetaStore now locks the complete
read/check/write against other claims and saves. A failed old delivery cannot
restore its event over a newer decision or onto a terminal run. Regression
coverage uses twenty concurrent claims across two store instances. File mode
remains a single-process deployment; this is not a cross-process filesystem lock.

## F06 — Intake deduplication could insert after losing its guard

NucleusIntakeStore fell through to INSERT when KV setNX lost and the winning
row was not visible yet. It now returns the existing row or a retryable error,
never inserts without the guard, and rechecks after acquiring it. The restored
Nucleus instance passed an intentionally delayed winner insertion and ten
concurrent launch claims via `scripts/check-intake-concurrency.mjs`.

File intake now serializes proposals/claims across handlers, writes atomically
and refuses unreadable state instead of silently discarding dedupe records.
Team requests retain their keys after dismissal. The composer saves the request
ID with the draft, restores it after failure/reload, and rotates it when the
intent changes. Reusing a key for different content reports a conflict.
Browser verification intercepts the POST locally and checks recovery without
launching a run or spending model budget.

### Recovery continuation (2026-09-21)

New Nucleus tasks now use an additive primary-key table. Deterministic
key/generation IDs replace the expiring insert guard; delayed writers cannot
mint another task after a lease expires. Legacy tasks remain readable and
updatable. The real-engine probe covers delayed inserts, concurrent claims,
dismissal and reopening; restart persistence was checked separately.

Accepted launches use an immutable journal. Start events can be repaired, and
Nucleus metadata/scheduler publication plus its receipt commit in one SQL
transaction. The worker repairs bounded pages of accepted launches, isolates
corrupt records and never resets completed work. Isolated-engine fault injection
covers concurrent writers, rollback, lost commit responses and engine restart.
A large-request probe exposed inline-row overflow in metadata publication; its
display summary is now byte-bounded while the full request remains in the journal
and events. Long stable submission IDs also wrap in the mobile breadcrumb.

The worker no longer resets intake claims merely because no event exists yet:
that could race the original enqueue. Interrupted claims remain visible in the
Inbox with an authorized same-ID retry. Once automatic launch begins, ambiguous
failures retain the claim and reservations until recovery rather than silently
starting a second operation. Pre-admission refusals still return to proposed.

Direct dashboard launches persist a draft request ID and bind it to the
actor and submitted intent. Changed content under the same ID conflicts;
retries preserve the accepted configuration and completed status. Browser
verification actually drops an accepted response and retries the restored draft.

Limits: follow-up submissions and parent-review cancellation still need a shared
durable operation; source/whole-fleet reservation reconciliation and operator
resolution of permanently invalid held intents remain open. No universal
exactly-once guarantee. A process interrupted before durable acceptance needs
an explicit Inbox retry. File mode remains single-process. See UPGRADING.md
for the coordinated storage rollout; these changes do not close S03/S04/S11.


### F06 continuation — durable follow-up and review replacement

Follow-up submissions now bind actor, parent, request ID and submitted content.
The browser retains the message and choices with that ID; accepted retries bypass
mutable configuration/forge resolution and return the same child. Changed content
under the same key is refused. Current permissions still apply on retry.

The accepted launch intent records a review-parent prerequisite. Publication
claims a durable owner token, records parent cancellation and only then makes
the child runnable. Worker recovery retries this operation after a crash. Generic
failed-decision release cannot overwrite a revision owner. Admission refusals
occur before acceptance and leave the original review untouched. Old worker
versions cannot safely publish this new intent; coordinated rollout is required.

Proof includes competing revisions, concurrent retries, failure before cancellation,
actual isolated-engine restart and browser accepted/lost-response retry. A browser
probe caught a controlled-checkbox/native-event race; plan input now updates its
state before the draft listener rerenders. The Nucleus generic release uses SQL
IS NULL because the document filter stringifies null; positive release and negative
revision-owned release are both exercised on the real engine.

Still open: permanently conflicted accepted intents need an operator resolution
workflow; external forge outcome reconciliation and durable approval delivery are
separate operations. This does not close all of F06 or the release programme.


### F03 continuation — project name and clone URL binding

A fresh isolated reproduction stored `team/expected` with clone URL
`https://forge.example/team/different` and `requirePlanReview:true`. Bare-key
lookup returned the policy, but lookup by the allowed clone URL returned null.
This is an operator configuration hazard: it can make configured review or budget
policy ineffective for the repository the project actually allows. No such
mismatch was found among the 18 live projects in the read-only inventory.

Shared project normalization now refuses mismatched repository names and clone
URLs before storage, covering UI/CLI/integration writes. Tests cover direct store
and settings action rejection without a partial record. An older evidence test
used an unrelated URL as arbitrary fixture data; it now uses the correct URL.
Existing malformed legacy data still requires an explicit repair/migration; do
not invent a forge binding for URL-less records. Canonical multi-forge storage,
reviewer rules, intake lookup and statistics migration remain open together.


### F07 — credential-bearing project clone URLs

The generic project store accepted HTTP URL userinfo, unlike guided setup. An
operator pasting such a URL could persist a credential in ordinary project
configuration exposed by project listings. Reproduced using synthetic credentials;
read-only live inventory found none. Shared normalization now rejects embedded
credentials, query/fragment suffixes and unsupported clone schemes. Errors never
echo the supplied URL. Direct-store and actual settings-action tests prove refusal
without a partial record or credential in the redirect. Configure repository
authentication separately through the existing credential configuration.


### F03 continuation — full-origin identity migration

Project storage now uses canonical full clone URLs, retaining legacy source
records in a separate table/file. Same-named repositories have independent
configuration; ambiguous short-name reads and mutations are refused. UI links,
intake lookups, reviewer rules, telemetry targets and statistics use this scope.
Historical statistics and memory require the original run's recorded origin;
legacy spend without a run identity remains unmodified and cannot support an
exact-origin ratio. New runs record a memory/index scope version; old paused
inputs retain their original scope and step sequence.

The isolated Nucleus restore proof covers all 18 legacy projects, transaction
rollback during import, concurrent initialization/registration, forge isolation,
explicit binding and deletion without re-import. It caught a malformed unbound
legacy record; migration preserves such records for inspection/removal while
validating new writes. The storage cutover/rollback limits are in UPGRADING.md.
Deployment and final validation are tracked separately; this implementation is
not a claim that the entire release programme is complete.


### F08 — Setup verification spent model turns after deterministic checks

The setup action requested an agent-backed scan even though the runtime had
already recorded checkout, preparation and test results. New setup requests
now record a setup-only flag and distinct admitted step prefix, finish with no
model calls, and release the sandbox on success/failure. Older check inputs
retain their recorded behavior. Replaying completed checks after sandbox release
works without re-executing commands. Real sandbox positive and negative checks
used the existing isolated fixture: the Python suite passed, an explicit failing
command failed, neither called a model, and both released their sandbox.

### F09 — Web wrapper did not forward shutdown signals

The coordinated identity cutover exposed a full Docker stop timeout: the CLI
parent did not forward SIGTERM to its web server child. The wrapper now forwards
SIGTERM/SIGINT. Isolated actual-server checks confirmed both the parent and
listener stop promptly, without leaving an orphaned server. This is a process
lifecycle fix; it does not establish generic request/drain guarantees.
